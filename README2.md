## 1. 背景与目标

### 1.1 业务背景

Polymarket 是一个去中心化预测市场平台，用户可以在各类事件（如比特币涨跌、体育赛事结果、温度预测等）上进行交易。平台通过 WebSocket 实时推送订单成交数据。为了支持前端图表化展示价格走势、交易量等指标，需要将这些高频的、离散的订单数据转换为标准的 K 线（OHLCV）数据，并提供高效的查询能力。

### 1.2 业务痛点

- 原始订单数据量大（每秒可能几十到上百条），直接存储和查询成本高。
- 前端需要展示不同时间粒度（5分钟、1小时、1天等）的价格走势，手动聚合非常低效。
- 不同市场的交易活跃度差异大，需要能够处理无交易的空白时间段（如凌晨）。
- 需要同时支持实时最新数据和历史数据的统一访问。

### 1.3 产品目标

构建一个可独立运行的实时行情聚合服务，能够：

1. **实时接收** Polymarket 的订单成交数据。
2. **秒级聚合** ：将每秒内的所有订单合并为一根秒级 K 线（开盘、最高、最低、收盘、成交量）。
3. **多周期K线** ：基于秒级数据，定时生成 5分钟、15分钟、30分钟、1小时、4小时、1天等周期的 K 线，并持久化存储。
4. **高效查询** ：对外提供 RESTful API，支持通过市场标识（slug）、结果索引等参数查询任意时间范围的 K 线数据，并自动处理缺失的时间区间。
5. **缓存加速** ：最近24小时的秒级数据缓存在 Redis 中，实现毫秒级实时数据查询。

## 3. 核心功能需求

### 3.1 实时数据接入与秒级聚合

| 功能               | 描述                                                                                                                                                                                                                                      |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **数据源**         | 连接 Polymarket 官方 WebSocket，订阅 `activity` 主题下的 `orders_matched` 事件。                                                                                                                                                          |
| **秒级聚合规则**   | 针对同一市场（slug + outcomeIndex）的同一秒内的所有订单，计算：``- `open`：该秒第一笔订单的价格``- `high`：该秒最高成交价``- `low`：该秒最低成交价``- `close`：该秒最后一笔成交价``- `volume`：该秒总交易量``- `tradeCount`：该秒成交笔数 |
| **无交易秒的处理** | 当查询要求“连续时间轴”时，系统会自动用上一秒的 `close` 填充缺失的秒（成交量、成交笔数为0）。若整个请求范围内没有任何真实数据，则填充0。                                                                                                   |
| **存储**           | 聚合后的秒级数据存储在**Redis** 中，并设置 24 小时自动过期。Redis Key 格式：`second_bar:{slug}:{outcomeIndex}:{timestamp}`。                                                                                                              |

**业务价值** ：将原始订单量压缩为秒级K线，存储成本降低一个数量级，同时为后续多周期K线提供标准的原子数据。

---

### 3.2 多周期K线生成与持久化

| 功能             | 描述                                                                                                                                                                                                                           |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **周期列表**     | 5分钟、15分钟、30分钟、1小时、4小时、1天。                                                                                                                                                                                     |
| **生成频率**     | 定时任务每隔 1 分钟执行一次，扫描所有活跃市场，并为每个未生成的周期窗口计算K线。                                                                                                                                               |
| **生成规则**     | 基于该周期内所有秒级K线（真实+填充）聚合得到：``- `open`：周期内第一秒的开盘价``- `high`：周期内最高价``- `low`：周期内最低价``- `close`：周期内最后一秒的收盘价``- `volume`：周期内总成交量``- `tradeCount`：周期内总成交笔数 |
| **存储**         | 多周期K线写入**PostgreSQL** ，并按市场、结果、周期、开始时间建立唯一索引，支持幂等更新。                                                                                                                                       |
| **历史数据保留** | 永久保留（可根据运营策略设置数据保留年限）。                                                                                                                                                                                   |

**业务价值** ：前端可以直接请求1小时的K线，无需实时计算，响应速度可达毫秒级，且支持任意时间范围的历史回溯。

---

### 3.3 新市场自动发现机制

| 功能         | 描述                                                                                                                   |
| ------------ | ---------------------------------------------------------------------------------------------------------------------- |
| **自动识别** | 当服务首次收到某个 `slug:outcomeIndex` 的订单时，系统将该市场记录到Redis集合 `active_markets` 中，并触发“新市场事件”。 |
| **事件用途** | 可扩展用于：`- 记录市场元信息到数据库`- 发送实时通知（如WebSocket推送到前端）``- 自动预热K线计算。                     |

**业务价值** ：无需人工配置市场列表，系统可自动跟踪所有出现交易的市场，适合预测市场数量动态增长的场景。

---

### 3.4 数据查询API

#### 3.4.1 请求参数

| 参数名   | 类型   | 必填 | 默认值        | 说明                                                                                                                 |
| -------- | ------ | ---- | ------------- | -------------------------------------------------------------------------------------------------------------------- |
| slug     | string | 是   | 无            | 市场标识，例如 `btc-updown-5m-1777114200`                                                                            |
| start    | int64  | 否   | 当前时间-3600 | 开始时间戳（秒，UTC）                                                                                                |
| end      | int64  | 否   | 当前时间      | 结束时间戳（秒，UTC），不会超过当前服务器时间                                                                        |
| interval | int    | 否   | 1             | 返回数据的粒度（秒），例如 60 代表返回1分钟K线。支持1秒及以上的任意整数。                                            |
| fill     | bool   | 否   | true          | 是否自动填充缺失的时间点。`true` 时返回连续时间轴（缺失点用前一 close 填充）；`false` 时只返回实际有交易的秒级数据。 |
| limit    | int    | 否   | 1000          | 返回的最大数据点数（按时间顺序取前 `limit` 条或尾 `limit` 条？按产品设计：取从 `start` 开始的连续 `limit` 条）。     |

#### 3.4.2 响应格式

**json**

```
{
  "slug": "btc-updown-5m-1777114200",
  "outcomeIndex": 0,
  "interval": 60,
  "count": 1000,
  "data": [
    {
      "startTime": 1777114200,
      "endTime": 1777114259,
      "open": 0.65,
      "high": 0.68,
      "low": 0.64,
      "close": 0.67,
      "volume": 1250.5,
      "tradeCount": 42
    }
  ]
}
```

#### 3.4.3 业务规则

- 如果 `start` 到 `end` 的范围超过 `limit`，则只返回从 `start` 开始的连续 `limit` 个数据点（尾部截断）。
- 默认 `interval=1`（秒级），前端可以根据屏幕宽度和缩放自动调整 `interval` 值，例如放大到1分钟（60）或5分钟（300）。
- 返回的数据按时间升序排列。

    **业务价值** ：

- 一个接口同时支持实时秒级数据、多周期K线、历史数据回溯。
- 前端无需复杂聚合，直接渲染图表即可。
- `fill` 参数让前端自由选择是否需要连续时间轴（例如非交易时段是否显示平线）。

### 3.5 系统监控与健康检查

| 功能                  | 描述                                                                    |
| --------------------- | ----------------------------------------------------------------------- |
| **WebSocket连接状态** | 自动重连（指数退避），最大重试10次，超过后触发告警。                    |
| **Redis健康检查**     | 提供 `/health` 接口，检测Redis连通性和内存使用。                        |
| **业务统计**          | 定时输出处理过的订单数、已聚合的秒级K线数、活跃市场数量、队列积压情况。 |

## 4. 非功能需求

| 类别           | 具体要求                                                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **性能**       | - 秒级聚合延迟 < 10ms（批量100条订单）`- 查询1小时秒级数据（3600条）响应时间 < 200ms`- 查询7天1小时K线（168条）响应时间 < 50ms |
| **可用性**     | - WebSocket断开后自动重连，丢数据期间可容忍少量积压。``- 服务进程异常退出时应自动拉起（使用 PM2 或 Docker）。                  |
| **可扩展性**   | - 支持增加新的预测市场而无需修改代码。``- 可横向扩展多个聚合实例，但需避免重复写入（使用Redis原子操作）。                      |
| **数据一致性** | - 秒级聚合使用Lua脚本在Redis中原子执行，无竞态条件。``- 历史K线生成采用Upsert，避免重复写入。                                  |
| **部署方式**   | - 独立 Node.js 进程，可通过 Docker 容器化部署。                                                                                |
| **安全性**     | - API可增加简单的API Key验证（可选）。``- 不对外暴露Redis端口。                                                                |

## 7. 验收标准

1. 服务启动后，能在日志中看到“✅ WebSocket connected successfully”及“📡 Subscribed to orders_matched”。
2. 当 Polymarket 有订单成交时，Redis 中每秒都会产生新的 `second_bar:*` key，且每个 key 中 OHLCV 聚合正确。
3. 通过 API 请求 `?slug=xxx&start=xxx&interval=60&fill=true`，返回的K线数量和时间范围符合预期，无未来数据。
4. 模拟连续多秒无交易，API 返回的数据中缺失秒被前一秒收盘价填充，成交量=0。
5. 服务重启后，已存在的市场不会重复触发“新市场”事件。
6. 在无任何订单的情况下，查询一个从未见过的 `slug`，返回正确的错误提示（“No data found”）。
